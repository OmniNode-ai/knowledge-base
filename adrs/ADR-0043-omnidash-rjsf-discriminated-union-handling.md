# ADR-0043: Render Pydantic-Generated JSON Schema With Stock @rjsf, No Custom Field

**Status**: Accepted (spike outcome)
**Date**: 2026-06-20
**Source**: omnidash `docs/adr/005-rjsf-discriminator-union.md` (filed in-repo as "ADR 005"; renumbered on migration into the platform-wide decision ledger)

---

## Context

Phase 0 of the contract-driven UI platform ships six Pydantic model primitives:

- `ModelComponentContract`
- `ModelActionContract`
- `ModelDataBindingContract`
- `ModelPermissionContract`
- `ModelEvidenceRequirementContract`
- `ModelRendererCapabilityContract`

These models power an in-dashboard contract inspector — an operator-facing form where a component contract can be viewed and edited. The inspector must:

1. Accept JSON Schema generated by Pydantic's `model_json_schema()`.
2. Render a usable form via `@rjsf/core` 6.x.
3. Validate and round-trip edits without data loss.
4. Handle the discriminated-union field (`ModelWidgetDefinition.config`, discriminated on `config_kind`) that ships alongside the Phase 0 primitives.

The spike question: does `@rjsf` 6.x consume Pydantic-generated `oneOf` + `discriminator` schemas without a custom Field or Widget?

## Decision

**Use `@rjsf/core` 6.5.1 + `@rjsf/validator-ajv8` as-is.** No custom Field or Widget is required for Phase 1 scope. Two UI gaps exist; both are resolved with `uiSchema` entries, not new library code.

## Findings

### Gap 1 — Nullable `anyOf` rendered as a branch toggle

**What Pydantic emits:**

```json
"permission": {
  "anyOf": [
    { "$ref": "#/$defs/ModelPermissionContract" },
    { "type": "null" }
  ],
  "default": null
}
```

**What @rjsf renders:** A oneOf selector widget with two branches — "Option 1" (the object form) and "None". This is technically correct but produces a confusing double-click flow for every nullable field in the contract (4 nullable fields in `ModelActionContract` alone).

**Resolution:** Set `ui:options: { label: false }` + a descriptive `ui:title` in uiSchema for nullable object fields, and/or use a custom `nullableObject` widget that collapses the null-vs-object selector into a checkbox. For Phase 1 (inspector-only, no operator-facing editing of nullable objects), the default rendering is acceptable. A `NullableField` custom widget is the **Phase 2** enhancement path if operator UX requires it.

### Gap 2 — Discriminator branch selector label is generic

**What Pydantic emits:**

```json
"config": {
  "oneOf": [ { "$ref": "#/$defs/ModelWidgetConfigChart" } ],
  "discriminator": {
    "propertyName": "config_kind",
    "mapping": { "chart": "#/$defs/ModelWidgetConfigChart" }
  }
}
```

**What @rjsf renders:** A select with labels "Option 1", "Option 2", … The `discriminator.propertyName` is used internally for branch matching (const-value comparison on `config_kind`) but is not surfaced as the label source.

**Resolution:** Add a `uiSchema` entry for the discriminator field:

```typescript
const uiSchema = {
  config: {
    config_kind: {
      'ui:widget': 'select',
      'ui:title': 'Widget type',
    },
  },
};
```

This renders the `config_kind` enum values (`chart`, `table`, `metric_card`, …) as the selector labels directly. Branch switching then works: selecting "metric_card" from the `config_kind` select sets `config.config_kind = "metric_card"` and @rjsf re-selects the correct `oneOf` branch on the next render cycle.

**One-sentence summary:** @rjsf 6.x reads `discriminator.propertyName`, uses `const` values in branch `properties` for selection, but does not auto-label from the discriminator field enum. The fix is a single uiSchema override — no custom widget.

### Gap 3 — AJV strict-mode rejects empty `anyOf` in nested schemas

**Observed:** When `@rjsf/validator-ajv8` internally compiles the `ModelWidgetDefinition` schema to match `oneOf` branches, AJV logs:

```
Error encountered compiling schema: Error: schema is invalid:
  data/anyOf must NOT have fewer than 1 items
```

This comes from an empty `anyOf: []` in a nested `$defs` entry (specifically `ModelSemVer.prerelease.items.anyOf` resolves to an empty array in certain schema-resolution paths). The error is logged but **does not crash the form** — @rjsf catches the AJV exception internally and falls back to exhaustive matching.

**Root cause:** Pydantic emits `anyOf: []` for fields whose type resolves to `never` or `Any` in edge cases. This is a schema-quality issue, not a Pydantic regression.

**Resolution:** Filter empty `anyOf` arrays out of the schema at emit time in the platform's TypeScript-type emitter, or use AJV `strict: false` in the inspector (already the default in `@rjsf/validator-ajv8`). For Phase 1, the logged warning is benign; the form renders and validates correctly. Tracked as Phase 2 cleanup.

### Gap 4 — Frozen Pydantic models are a runtime (not rendering) constraint

All Phase 0 contracts use `ConfigDict(frozen=True)`. This is transparent to @rjsf, which emits plain JS objects on change/submit events. The constraint becomes relevant at the bus-handler boundary: the handler that consumes edited formData must construct a **new** model instance (`ModelComponentContract(**data)`) rather than patching an existing frozen instance. This is not a rendering gap.

## Proof

The following was verified in this spike:

1. `@rjsf/validator-ajv8` validates the Pydantic-generated schema for all six Phase 0 primitives without errors (AJV `strict: false`, `allErrors: true`).
2. The `ModelWidgetDefinition.config` `oneOf` field selects the correct branch when `config_kind` is preset in formData (verified via the `getOptionMatchingSimpleDiscriminator` internal path in @rjsf utils — uses `property.const === formData[discriminatorField]`).
3. Submit round-trip preserves formData intact for both `ModelComponentContract` (nullable anyOf) and `ModelWidgetDefinition` (discriminated union).

Test file: `src/components/dashboard/contract-inspector/ContractInspector.test.tsx`
Proof-of-concept component: `src/components/dashboard/contract-inspector/ContractInspector.tsx`

## Consequences

- **Phase 1 path is clear:** the contract inspector can proceed using `@rjsf/core` plus the Pydantic-generated JSON Schema emitter, without adding a new library.
- **uiSchema is the extension point:** per-field UI overrides live in a uiSchema object keyed by field path. This is the official @rjsf override mechanism; it does not require forking the library.
- **Phase 2 enhancement (nullable fields):** if operator UX requires better nullable-field handling than the default oneOf toggle, a single `NullableField` custom widget covers all nullable fields across all six primitives.
- **No themed @rjsf package needed:** Phase 1 uses the unstyled `@rjsf/core` Form inside a container that inherits the dashboard's existing CSS variables.

## Evidence

Verified against the live omnidash tree at migration time: `@rjsf/core` `^6.5.1` is still pinned in `package.json`, and `src/components/dashboard/contract-inspector/ContractInspector.tsx` exists.
