## Task 1: Wire verification_sweep into merge_sweep as pre-merge gate

**Priority**: P0
**Source**: "On the Horizon" — Automated Output Verification Before Merge

### What to do

Add an optional `--verify` flag to `onex:merge_sweep` that runs `onex:verification_sweep`
checks on each PR after CI passes but before enabling auto-merge.

The core design work is the **changed-file-to-verification-target mapping** — teaching
merge_sweep how to select meaningful verification targets from PR changes. The flag
wiring and reporting split are straightforward; target selection is the real problem.

### Verification Target Mapping

Deterministic first-pass mapping from changed-file patterns to verification checks:

| Changed-file pattern | Verification target | Check |
|---|---|---|
| `src/**/projection*.py`, `src/**/projector*.py` | Projection table for that module | Table exists, row count > 0, sample row has all non-null required columns matching the Drizzle schema |
| `src/**/handler*.py` (Kafka consumer) | Projection sink + summary endpoint consuming it | Endpoint returns HTTP 2xx with structurally valid JSON matching expected response shape (required fields present, correct types) |
| `src/**/route*.py`, `src/**/api*.py`, `pages/api/**` | The modified API route(s) | Endpoint returns HTTP 2xx with non-error payload; response body contains expected top-level keys per route contract |
| `drizzle/**`, `migrations/**` | All projection tables in the affected database | Tables exist, migrations applied without error, row schema matches Drizzle definition |
| `topics.yaml`, `contract.yaml` (event bus) | Kafka topic exists + consumer group has zero or decreasing lag | Topic listed in `rpk topic list`, consumer group lag via `rpk group describe` |
| No pattern match | Skip verification for this PR | Logged as `skipped_no_mapping` in report |

This mapping is a first-pass heuristic. It does not attempt full semantic PR impact
analysis. Files not matching any pattern are skipped without penalty.

### Failure Categories

The merge report must distinguish these outcomes per PR:

| Category | Meaning | PR action |
|---|---|---|
| `merged` | CI passed, verification passed (or skipped by policy), auto-merged | None |
| `verification_failed` | Verification ran and returned a concrete failure | PR comment with failure details, skip auto-merge |
| `verification_unavailable` | Verification target unreachable (service down, DB unreachable) | Treat as neutral skip, not failure. Log warning. Do not block. |
| `verification_timeout` | Verification did not complete within 30s per-PR budget | Treat as neutral skip. Log warning. |
| `verification_tool_error` | verification_sweep itself errored (crash, bad config) | Treat as neutral skip. Log error. Do not block merge batch. |
| `skipped_no_mapping` | PR changes did not match any verification target pattern | Normal skip, no action needed |
| `skipped_by_policy` | `--verify` flag not set, or PR repo excluded from verification | Normal skip |

**Batch semantics**: A verification failure on one PR does **not** block other PRs in
the same sweep. Each PR is evaluated independently. If PR-B depends on PR-A and PR-A
fails verification, PR-B is still evaluated on its own merits (dependency-aware blocking
is out of scope for v1).

**Retry semantics**: No automatic retries in v1. A PR that fails verification is skipped
for this sweep cycle and will be re-evaluated on the next sweep if still open.

### Why

"garbage UUIDs in dashboards, missing migrations, unverified event flows" — merge-sweep
currently gates only on CI green, which passes with structurally correct but
data-incorrect code (a recurring pattern, seen 4 times across registration fixes).

### Acceptance

- `merge_sweep --verify` runs verification_sweep per-PR using the target mapping above
- Report splits PRs into all 7 categories listed above
- Verification failure on one PR does not block other PRs in the batch
- Verification unavailable / timeout / tool error treated as neutral skip (never blocks)
- PR comment on verification failure includes: which check failed, expected vs actual, target mapping used

### Files affected

`omniclaude/plugins/onex/skills/merge_sweep/SKILL.md`, `omniclaude/plugins/onex/skills/verification_sweep/SKILL.md`

## Task 2: Add PostToolUse hook for test-run reminder on handler/test edits

**Priority**: P2
**Source**: "Existing CC Features to Try" — Hooks

### What to do

Create a new PostToolUse hook that detects when an Edit or Write tool modifies a file
matching handler, projection, or test patterns, and injects an advisory reminder into
the agent's context that relevant tests should be run before committing.

This is a **first-pass file-pattern heuristic**, not broad semantic test-run enforcement.
It will not catch every relevant file. It is advisory only and never blocks execution.

### Hook Protocol

The hook uses the same injection pattern as `post-tool-use-ci-reminder.sh`:

1. Read PostToolUse JSON from stdin
2. Extract `.tool_input.file_path` via jq
3. Match file path against patterns
4. If matched: inject reminder into `.hookSpecificOutput.additionalContext` via jq
5. Print modified JSON to stdout
6. Exit 0 always (advisory, never blocking)

**Output shape** (jq transform on the stdin JSON):
```
.hookSpecificOutput.additionalContext += "\n\n[Test Reminder] ..."
```

This is the established Claude Code hook contract for context injection — the same
mechanism used by `post-tool-use-ci-reminder.sh` (lines 60-66).

### File Pattern Matching

First-pass patterns (intentionally narrow to avoid noise):

| Pattern | Rationale |
|---|---|
| `tests/**/*.py` | Direct test file edits should trigger test runs |
| `src/**/handler*.py` | Handler logic is the most common source of buggy_code friction |
| `src/**/projection*.py` | Projection modules directly affect data correctness |
| `src/**/projector*.py` | Alternate projection naming convention |
| `src/**/effect*.py` | Effect nodes produce side effects that need test coverage |
| `src/**/reducer*.py` | Reducer state logic is test-critical |

Files not matching these patterns do not trigger the reminder. This is intentional —
the hook is a targeted heuristic for the highest-friction file categories, not a
comprehensive test-enforcement system.

### Deduplication

- **Per-session dedup**: Track reminded file paths in `/tmp/omniclaude-test-reminder/`.
  If the same file path was already reminded in this session, skip. This prevents
  repeated edits to the same file from spamming reminders.
- **No per-edit dedup**: Different files in the same session each get one reminder.
- The dedup mechanism mirrors the debounce pattern in `post-tool-use-ruff.sh` (lines 73-93).

### Reminder Text

```
[Test Reminder] You just edited {filename} which matches a handler/projection/test pattern.
Run relevant tests (pytest tests/ -v -k {module_name}) before committing.
```

### Why

26 buggy_code friction events — agents edit handler code and commit without running
relevant tests (from "Where Things Go Wrong").

### Acceptance

- Hook registered in `hooks.json` with event `PostToolUse`, matcher `^(Edit|Write)$`
- Hook fires on Edit/Write to files matching the 6 patterns above
- Reminder injected via `.hookSpecificOutput.additionalContext` (same as CI reminder hook)
- One reminder per unique file path per session (deduped)
- Hook exits 0 always, never blocks
- Kill switch via `OMNICLAUDE_HOOK_TEST_REMINDER=0`

### Files affected

`omniclaude/plugins/onex/hooks/scripts/post-tool-use-test-reminder.sh` (new),
`omniclaude/plugins/onex/hooks/hooks.json` (register new hook)
